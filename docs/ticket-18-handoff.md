# Modal phase execution and lightweight Render dispatcher (#18)

The implementation is complete locally; accounts for Vercel, Render, Neon, R2 and Modal still require human signup. No provider resource, token, cloud build, deployment or paid resource was created. Actual cloud canary, termination acknowledgement, target Linux frozen-model parity, resource peak and credit/limit validation remain #15 release gates. The complete operator destination/configuration guide is [deploy/modal-render-runbook.md](../deploy/modal-render-runbook.md), with role-filtered dispatcher/worker/reconciler env examples. Prior single-host/browser-only deployment instructions are superseded.

`service.execution.ModalProvider` is the small SDK boundary. It submits the persisted operation ID, reconstructs calls by ID for nonblocking poll/cancel, treats unknown acceptance as ambiguous and only marks stopped after provider acknowledgement. Spawn/cancel are bounded to 12 seconds; polling uses the SDK's own `get(timeout=0)` rather than canceling its explicitly non-cancellation-safe coroutine. Unknown acceptance has a 30-second backoff and three-registration cap, always the same logical operation. Known calls are not resubmitted. Unknown provider/transport errors preserve current ownership/canceling rather than pretending stopped. Returned/expired calls without saved completion are terminated and recorded explicitly interrupted, not lease-stolen.

`service.modal_worker.run_phase` FIRST claims with its actual provider call ID, fresh per-input UUID and fence before source/native imports. Migration 002 adds that attempt identity; schema-owner initialization applies both ordered migrations, while runtime performs no DDL. Duplicate input claims fail even if Modal redelivers with the same FunctionCall ID. There is no lease takeover or automatic retry of canceled/terminal work. The context-local native transport reuses the original actual fixed `service.app` orchestration and stage contracts, without mutating global tool implementations or numerical source files. The entire phase owns progress independently of Render/browser lifetime.

The imaging input selects/downloads only pinned manifest/R2 assets, executes actual QC/masks/features/eligibility, persists real events/features/verified R2 artifact references, and either completes clean scoring/evaluation or returns its compute immediately at the persisted gate. Approval on Render validates the exact persisted model/disclosure and creates one durable scoring intent. Its worker downloads static assets only (`scans=False`) and rechecks expected eligibility with the unchanged model tool before scores. A changed outcome disclosure opens another gate. Missing outcomes still permit scoring, and fixed full-held-out versus selected exploratory evaluation remains unchanged.

Cancellation persists a tombstone first, then acknowledges **every known submitted/owned input across both phases**, including the gate-return tail. Queued unknown inputs cannot claim afterward. Provider outage leaves retryable canceling; no local task/engine acknowledgement substitutes for Modal. The worker independently watches durable ownership/cancellation while its native child runs. `NativeTools` owns each native process group and inherited lifetime pipe, kills/reaps its child on cancellation, cleans temporary workspace, and ensures an abruptly lost input closes the watchdog capability. Container disposal owns scratch after SIGKILL. Late publications cannot pass the call/attempt/fence/cancel checks.

`deploy/Dockerfile.dispatcher` includes only FastAPI/HTTP/Postgres/S3/Modal packages and the lightweight service files. `service.dispatcher` fails closed on missing remote configuration or ephemeral artifact storage and starts no imaging engine. `/health` does not touch Neon/provider APIs. The Modal image separately pins the original Python/native contract plus Modal 1.6.4 and exact SDK dependencies; its candidate bounds are 1 CPU hard, 4,096 MiB request/6,144 MiB memory limit, 16,384 MiB ephemeral disk, 1,800-second execution/600-second startup, two maximum single-use containers, retries/minimum/buffer zero. These are qualification settings, not a measured cloud guarantee or zero-cost promise.

There is **no scheduled/idle polling function**. Accepted phases continue without Render. Committed intent lost before provider acceptance waits for startup/authorized reconnect/control or a manual bounded `reconcile_pending`/CLI invocation; the runbook makes this limitation explicit. Frequent idle cron would prevent Neon scale-to-zero, so it is not enabled. Browser gate-idle polling correction is being delivered separately by the integration coordinator and must be included before release.
