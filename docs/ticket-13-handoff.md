# Browser-saved approval recovery (#13)

`POST /runs/restore` accepts only `{checkpoint}` and the original per-run Bearer secret. It validates a server HMAC binding the entire numeric checkpoint, original run ID, exact selected cohort, disclosure/generation, model/feature contract, eligibility report, and last audit sequence to that secret. It returns the same logical ID and pending status, never a replacement secret. Validated held-out catalog/model metadata remain trusted server assets; browser-provided executable models, paths, artifacts, and audit events are not accepted.

The browser saves the gate, named dispositions, feature vectors, pinned model context and ordered audit prefix into IndexedDB before displaying “Approval gate saved in this browser.” A saved pending gate recovers on worker 404 only when its identity, selection, complete local event prefix, and exact cursor agree. Restoration itself emits no event and performs no scoring or imaging. Existing events and Blobs stay local; the server retains only continuation events starting at the signed cursor + 1. Snapshots expose `sequence_base` and `last_sequence`; replay before the retained prefix is rejected explicitly. Explicit approval reuses #9's live outcome revalidation and score-worker guard; changed exclusions need a fresh disclosure/approval.

Normal reconnect remains unchanged for interrupted active computation, unusable secrets and lost local data. Incompatible/unsigned/edited checkpoints preserve available local History and explain the need for a new run. A concurrent restore that finds a newer disclosure reconnects to that disclosure. Duplicate restores and approvals retain the current owning process's state and never schedule duplicate scoring. Completed browser History never attempts restoration. Pending gates occupy the browser's one active-run reservation but no active compute task or engine subprocess; there is no age/deadline field or arbitrary expiry.

## Required operator configuration

The runner now **refuses startup** without `CHECKPOINT_SIGNING_KEY` of at least 32 characters. Generate a cryptographically random operator secret once using a secret manager, configure it on the external runner, and retain the same value across runner replacement. Keep it out of `NEXT_PUBLIC_*`, browser storage, logs, repository and example artifacts. Next/Vercel needs no copy. No ephemeral fallback is provided because it would silently invalidate saved gates after restart. Losing/rotating this key invalidates old checkpoints; retain the previous deployment's immutable catalog/model assets and key for indefinite compatible recovery. This durable deployment configuration is allowed; visitor run/event/result state is still never persisted server-side.

Deployment ownership remains one external runner process plus its private engine. Ordinary duplicate controls and concurrent restores are serialized within that owner; there is no durable cross-restart per-run replay ledger. A person deliberately retaining an obsolete signed gate and its secret could resubmit it after all temporary server state has again vanished. Global malicious replay prevention would require durable visitor tombstones, contrary to ADR 0001. The normal browser restores only its latest saved pending prefix, and never restores terminal History or reuses a prior gate for another selection/model. Reopen ADR 0001 before claiming global historical replay revocation.

Restore requests include only compact numeric features/report/context, never prior PNGs or the complete audit log. The browser, Next proxy (actual streamed bytes), and runner enforce a 4,000,000-byte request ceiling below Vercel's 4.5 MB limit. Prior artifact bytes stay in IndexedDB. There is no hosted payload/deployment claim here.
