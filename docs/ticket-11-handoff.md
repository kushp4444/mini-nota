# Confirmed cancellation and browser coordination (#11)

`POST /runs/:id/cancel` uses the same per-run Bearer secret as reads. It serializes repeated controls, freezes execution as `canceling`, asks the private engine to stop, then cancels the runner task and appends exactly one `done` event with status `canceled` and a reason. Available stage results remain in snapshots and browser History. A completed/failed/canceled run keeps its original terminal outcome on repeated cancellation. Late stage responses cannot append results or advance a frozen/terminal run. Engine unavailability returns 503 and retains `canceling` for an explicit retry; it never claims the process stopped without confirmation.

Private engine stage requests carry `operation_id` (the run UUID). `service.engine_api` runs each stage in an isolated Python subprocess/process group through `service.engine_worker`, retaining portable artifact bytes before workspace cleanup. `/operations/:id/cancel` kills the active process group, waits for its exit and temporary workspace deletion, and retains an in-memory cancellation tombstone so delayed HTTP requests cannot restart that run. Tombstones expire after one hour; private requests time out after five minutes. Worker configuration `ENGINE_WORKER_MODULE` defaults to `service.engine_worker`; tests supply a clearly labeled slow executable fixture at this external numerical boundary. It is operator configuration, never browser input. There is no durable visitor server state.

`web/lib/browser-run.ts` uses a short Web Lock to reserve an opaque active-run marker in browser localStorage before launching. Concurrent tabs cannot both reserve it. The marker survives page closure and disconnects, including an unanswered approval; only a known terminal outcome releases it. Separate browser storage contexts are independent. Unsupported Web Locks or inaccessible localStorage fail safely with an explanation. A launch whose HTTP result is lost retains its pending marker because the browser cannot prove that the server did not start work; this conservative case needs the reconnect slice to explain the missing run reference rather than silently creating a duplicate.

The page reserves before clearing the active view, attaches the server-issued ID after creation, and releases on terminal persistence. `CancelRun` opens an explicit confirmation; Keep running sends no cancellation. Confirmation posts cancel, collects the authoritative snapshot, and saves its existing events/results to History. `captureEvent` keeps a terminal local record stable against late events.

## Reconnection and gates integration

- #12: preserve `reserveBrowserRun` / `attachBrowserRun` in start, `releaseBrowserRun` on terminal save, and `watchBrowserRun` UI subscription. Reconnecting a saved unfinished run should reestablish its marker if it predates this slice. The marker is a browser-local run reference, not a visitor/account/session identifier.
- #12: abort the current polling connection before the cancel snapshot is consumed, or drain the authoritative cursor through `follow`; do not let an old in-flight callback replace the canceled record. Prefix writes from other tabs must not overwrite a later terminal IndexedDB record (#12 is adding a monotonic transaction guard).
- #9: approval controls must serialize on the run's existing `control_lock`, reject terminal/canceling outcomes before creating any task, and keep the marker while waiting. Pass `run['id']` to every `invoke_stage`; check `run['status'] == 'running'` after awaited results before appending or advancing.
- Additional engine stages should be `async` HTTP handlers calling `await run_stage(stage, selection, authorization)`; the isolated worker already passes stage names to EngineWorkspace generically.
